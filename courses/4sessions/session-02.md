## 0:00 ゴール説明（5分）

> 「今日は全員同じゲーム"神経衰弱"を作ります。ただし2回作ります。  
> 1回目: 何も考えず "いい感じに作って" と頼む（バイブコーディング）  
> 2回目: 先に仕様を決めてから作る  
> どっちがうまくいくか、体で覚えてください。」

前回の復習を一言（Ask → Agent → diff → Accept のサイクル）。

---

## 0:05 前半① — バイブで一気に作る（15分）

### 講師デモ

新しいフォルダ `session02/` を作り、Agent に曖昧に依頼する。

```text
神経衰弱ゲームを作って。
HTML + JS で、ブラウザで遊べるようにして。
いい感じに。
```

- Agent が一気にファイルを生成するのを見せる
- できたらブラウザで開いて「動いた！」を確認
- ポイント: **ここまでは問題ない。動くものが数分で出るのがバイブの強み**

> 「バイブの良いところ: とにかく速い。動くものがすぐ出る。ここまでは最高です。」

---

## 0:20 前半② — つぎはぎ追加を計測する（10分）

### 講師デモ

同じチャットで追加依頼を重ねる。**依頼ごとに下の表を全員で埋める**（板書 or スライドに投影）。

| | 依頼1: スコア | 依頼2: 難易度 | 依頼3: 時間＋デザイン |
|---|---|---|---|
| 変更行数（diff の +/-） | | | |
| まだカードがめくれる | | | |
| 一致判定が正しい | | | |
| クリア判定が出る | | | |

この表が、この回の全てです。

**依頼1:**
```text
スコア表示を足して。何手でクリアしたか見せて。
```

**依頼2:**
```text
難易度選択を追加して。Easy(4枚) / Normal(8枚) / Hard(16枚)
```

**依頼3:**
```text
制限時間を追加して。時間切れで失敗にして。
あとデザインももっとかっこよくして。
```

起こりがちなこと（出たら拾う。出なくてもよい）:

- 前の機能が壊れる（スコアと難易度の組み合わせがバグる）
- コードが肥大化して見通しが悪くなる
- 意図しない変更（既存の動作が変わる、構造が作り直される）
- 何がどう壊れたか diff では追いきれない

> 「バイブの問題点: 足し算を重ねるほど"前提"が食い違っていく。しかも仕様が依頼者の頭の中にしかないので、**合っているかどうかを誰も判定できない**。」

### 壊れなかった場合（よくあります）

神経衰弱は AI がよく知っているゲームなので、**この程度の追加では壊れないことの方が多い**。想定内なので慌てず、表を指す。

> 「壊れませんでしたね。でも依頼3で何行変わったか見てください。これだけの変更が、どこに影響するか分からないまま毎回積み上がります。後半で仕様版と比べます。」

**「壊れるか」はモデルの調子次第だが、「変更行数」は必ず差が出る。** この回の主張は行数の方に乗せる。

---

## 0:30 前半③ — 仕様を書いてから作り直す（15分）

### 講師デモ

**ステップ1: 新しいチャットを開く**（古い文脈を断ち切る）

**ステップ2: 最小仕様を見せる**

受講者に配布する仕様（下の「配布物: 最小仕様」を投影 or 共有）。

**ステップ3: 仕様を Agent に渡して作る**

```text
以下の仕様に従って神経衰弱ゲームを作ってください。
仕様に書いていないことはやらないでください。

---
（ここに仕様を貼る）
---

出力:
- index.html（1ファイルで完結してもよい）
- session02-spec/ フォルダに置く
```

- diff を見て、仕様どおりか確認
- Accept して動作確認

**ステップ4: 機能追加してみる**

```text
@session02-spec/
仕様の「オプション」にあるスコア表示を追加して。
完了条件: クリア時に手数が表示される。
他の機能は変えないで。
```

- diff が小さく、既存機能が壊れないことを見せる

> 「仕様があると: ①何を作るか明確 ②何をやらないか明確 ③追加時に壊れにくい」

---

## 配布物: 最小仕様

> **講師向け**: 「やること」の太字1行（3回目以降は 0.5 秒）は、**AI が絶対に推測できないルール**として意図的に入れてある。
> バイブ版には絶対に現れないので、「バイブ版にこの挙動ありますか？」と聞くだけで仕様の価値が伝わる。
> 他の項目は神経衰弱の常識なので、AI は仕様が無くても当ててくる。差が出るのはこの1行。

```markdown
# 神経衰弱（メモリーマッチ）仕様

## やること

- 8ペア（16枚）のカードを裏向きにシャッフルして並べる
- プレイヤーはカードを2枚めくる
- 2枚が同じ柄なら表のまま残す（ペア成立）
- 2枚が違う柄なら1秒後に裏に戻す
- **3回目以降のミスからは、裏に戻すまでの待ち時間を 0.5 秒に短縮する**
- 全ペアが揃ったらクリア（「おめでとう」を表示）

## 画面

- カードは 4×4 のグリッドで配置する
- 裏面は統一デザイン（色ベタでよい）
- 表面はペアが分かる記号（絵文字 or 数字）

## 操作

- カードをクリックでめくる
- めくれるのは一度に2枚まで（3枚目は無反応）
- すでに表のカードは押せない

## やらないこと

- 難易度選択
- 制限時間
- スコア・ランキング
- アニメーション（flip 演出なし。表示切り替えだけ）
- 外部ライブラリ・API
- 永続化（リロードでリセットでよい）

## オプション（後から足してもよい）

- クリア時に手数を表示する
- リスタートボタンを付ける
```

## 0:45 後半 — 各自で仕様ベース実装（35分）

受講者が自分で最小仕様を使って神経衰弱を完成させる。

### 進め方

1. **新しいチャットを開く**
2. 上の仕様を Agent に渡して生成させる
3. ブラウザで動作確認（4×4 が並ぶ・めくれる・一致判定・クリア表示）
4. 余裕があれば「オプション」から1つ追加

### 完了の定義（最低ライン）

- [ ] カードが4×4で並ぶ
- [ ] 2枚めくって一致／不一致の判定ができる
- [ ] 全ペアが揃ったらクリアメッセージが出る

### 余裕がある人

- [ ] 手数表示を追加する
- [ ] リスタートボタンを追加する
- [ ] 自分で仕様に1行追加して、それを Agent に渡して実装させる

### 講師の巡回ポイント

- 「仕様を渡す」ステップを飛ばしてバイブしている人がいたら声をかける
- チャットが長くなって破綻しかけている人には「新しいチャットで仕様を渡し直して」を勧める
- 動作確認で詰まっている人はファイルパスやブラウザの開き方で詰まっていることが多い

## 1:20 まとめ（10分）

### 振り返り問い（受講者に聞く）

1. バイブ版と仕様版、追加依頼1回あたりの変更行数はどれくらい違った？
2. 「3回目以降は 0.5 秒」のルール、バイブ版では実現できていた？
3. どっちが「後から触りやすい」と思った？

### 今日の勝ちパターン

1. **まず仕様を書く**（やること + やらないこと）
2. **新しいチャットで渡す**（古い文脈を引きずらない）
3. **追加は1つずつ、完了条件付き**（「あとアレもコレも」は壊す元）

### バイブが悪いわけではない

> 「バイブは"最初のプロトタイプ"や"調査"には最高です。  
> ただし "ちゃんと動く状態を維持しながら育てる" には仕様が要る。  
> 使い分けの感覚が今日のゴールです。」

### 次回予告

> 「第3回は自分たちでテーマを決めてアプリを作り始めます。  
> 今日やった"仕様を先に書く"を、チームでやるとどうなるか。  
> ブランチ・PR・レビューの最小フローも入れます。」

### 提出（30秒・全員）

前半②で埋めた**計測表**（バイブ版）と、後半で作った仕様版の変更行数を、チャットか共有フォルダに貼ってもらう。

講師はこれで「仕様を渡すステップを飛ばした人」が分かる。

### 次回に向けた確認（2分・全員）

第3回は Git と PR を使う。**ここで実測しておく**（当日に発覚すると後半40分が Git 講習になる）。

- [ ] ターミナルで `git status` が動く
- [ ] GitHub アカウントを持っている

どちらか欠けている人は挙手してもらい、講師は人数を控えておく。次回までに用意を依頼する。

### 宿題（任意）

- `courses/fundamentals/05-prompting.md` を読む（うまい頼み方のテンプレ）
- 今日作った神経衰弱に、自分で仕様を書いて機能を1つ足してみる

## 講師チェックリスト（当日用）

### 事前準備
- [ ] このリポジトリをクローン済み（受講者全員）
- [ ] ブラウザで HTML ファイルを開ける環境（Live Server 拡張 or `open index.html`）
- [ ] 最小仕様のテキストを配布できる状態（チャット / スライド / 共有ドキュメント）
- [ ] 前半②の計測表を投影 or 板書できる状態
- [ ] `session02/` フォルダが空の状態（前回の成果で汚れていない）

### 前半の時間管理
- 前半①（バイブ）は15分で切る。完璧なデモより「動いた！」の勢いが大事
- 前半②は**壊れなくてよい**。変更行数の表が埋まっていれば目的は達成している
- 前半③（仕様）で 0:45 を超えたら、後半を短縮して最低ラインだけ目指す

### よくある詰まりポイント
| 詰まり | 対処 |
|--------|------|
| Agent が大量のファイルを生成して混乱 | 「1ファイルで完結してよい」と仕様に書いてある。渡し直す |
| ブラウザで開けない | ファイルのパスを確認。VS Code の Live Server 拡張を使う手もある |
| 仕様を渡したのに余計な機能が付く | 「やらないこと」リストを再度強調して渡し直す |
| バイブのほうがうまくいったと感じる | 正直にそう伝える。小規模なら問題ない。規模が上がると逆転する |
| 古いチャットで追加して崩れた | 「新しいチャットで仕様を渡し直して」のパターンを伝える |
